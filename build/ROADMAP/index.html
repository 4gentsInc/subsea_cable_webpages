    Roadmap: from a written plan to an adaptive workflow¶

    Updated: 2026-10-09 (Asia/Seoul). This is a development roadmap, not a release schedule or language specification.

    Write the work once. Run it with your tools. Change what comes next when the results change your mind.

    That is the experience Subsea Cable is working toward. Your agent keeps a readable Voyage Plan for dependencies and choices; your existing tools do the actual computation. When a result challenges the original strategy, the agent should be able to inspect the evidence and author a better next step while preserving the history of decisions already committed.

    Where we are¶

    You can write and review Voyage Plans today. Runtime foundations have been implemented and exercised in controlled prototype tests, including result routing, completion, and revision behavior. The next delivery goal is a reproducible execution demo with a real Host, followed by a separate demonstration of an Agent investigating results and changing its strategy.

    There is no supported public Runtime package or public runnable demo command yet. Prototype evidence and an accepted language contract are distinct from a feature you can install. Runtime availability records the current support boundary.

    The execution demo comes first. The Agent revision demonstration follows it and also requires a supported live evidence surface. Host interoperability is a related development track; a protocol definition alone does not deliver a working integration. These stages have no promised release dates.

    The point where you might want to try it¶

    See your own plan execute¶

    Start with a bounded workflow such as fetching data, transforming it, and publishing a report. The first execution milestone should let you see how an explicit plan becomes real work, how results reach dependent steps, and how you know the input has finished. The initial demonstration is deliberately small; a completed demo will establish that execution path, not production support for every workflow.

    You should be able to judge the integration from runnable evidence before committing a real workload. Supported tool connections and installation instructions will need their own delivery evidence.

    Change strategy when a successful response exposes a bad assumption¶

    Imagine an agent collecting a changing list from an API. Every request succeeds, but new records shift the pages and the agent starts receiving duplicates. Retrying the same request does not fix the strategy.

    The planned Agent demonstration asks it to inspect the relevant request, response, and selected plan; identify the broken assumption; then author a new collection strategy for later work. The review should show why it changed the plan and which later work used the revision. Previously committed history stays intact. The agent makes the judgment; the Runtime executes the authored plan.

    This is a bounded acceptance scenario, not a claim of automatic diagnosis or correct collection under every possible data change. Live inspection remains an open capability, and a revision cannot change work that has already committed.

    Keep the tools you already use¶

    The longer-term aim is to let workflow structure survive a change of tool or Host implementation. You should be able to evaluate a connection by its stated capabilities and reproducible compatibility checks. Host integration and verification are being developed toward that goal; arbitrary tools, SDKs, and plug-and-play connections are not available today.

    Further out: easier operation and reuse¶

    The tracked backlog also includes operator interfaces, better observation and retention of results, and verification for additional deployment arrangements. Recovery and safe reuse are directions to investigate, not delivery commitments: a retained handle does not prove crash recovery, and reusing structure does not authorize skipping or repeating an external effect.

    Dates, supported profiles, and installation links will be added when evidence justifies them. A stage advances on demonstrated user capability, not on the number of closed issues.

    Bring the workflow you want to try¶

    Prepare one Voyage Plan and describe the tools, expected results, and the point where new information might change your next step. That gives the project a concrete adoption case to test.

    Share a use case or report a gap through the public community repository. You do not need a Runtime implementation to explain the capability that would make you try Subsea Cable.
