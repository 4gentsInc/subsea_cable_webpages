    SCP-0015 — Vessel Control Plane, Cable Data Plane, and Agent-Authored Replanning¶

    • Status: Accepted
    • Author(s): on-the-ground owner with Codex
    • Created: 2026-09-27
    • Updated: 2026-09-28
    • Requires owner decision: no
    • External implementation ADRs: Vessel control-plane issue, Cable data-plane issue, and Runtime boundary/placement issue
    • Evidence repositories/revisions: owner direction and conflict inventory in language issue #22; existing Vessel implementation is not design authority
    • Activation pull request: #26
    • Effective language revision: the commit on main produced by squash-merging PR #26
    • Supersedes: in part, SCP-0001 (Carousel as the autonomous owner of speculative replenishment and direct receiver of Touchdown-consumption acknowledgement), SCP-0002 (Vessel as the whole-Runtime metaphor, Carousel ownership beyond atomic deduction, and undifferentiated Runtime ownership of the Outcome & Value Store), SCP-0004 (Vessel as the complete Consumer Runtime and outward product boundary; ownership of final voyage-result assembly), SCP-0006 (one undifferentiated Vessel owning the whole live loop), SCP-0011 (policy interpretation described as occurring inside a whole-Runtime Vessel), and SCP-0014 (Vessel ownership of laid-Cable channel execution, data-plane termination, and planned Goal-step memo work)
    • Superseded by: —

    Summary¶

    The Subsea Cable Runtime is the deployment-neutral whole. It contains two logically separate planes:

    • the Vessel control plane, which owns a voyage's open structural future, coordinates explicit Scheduler demand and speculative structural demand, invokes Carousel, and publishes newly committed structure; and
    • the Cable data plane, which operates only structure already published to it, including channels, buffering, backpressure, routed Values, grounded-leaf execution, output multiplicity, and terminal propagation.

    Carousel is not a control plane. It is the Vessel's demand-scoped mechanism for atomically resolving and applying one occurrence's reduction rule. It does not own the voyage, Cable lifecycle, channel execution, or Host streaming.

    An Agent or operator—not Vessel—authors replanning. After observing Cable Values, outcomes, or terminals, an authorized author may store new immutable Goal artifacts and atomically move a Name/Arity alias. Every unqualified occurrence remains free to observe the current alias until that occurrence is demanded. Earlier committed deductions and installed topology remain immutable.

    The planes are separated by an implementation-independent boundary. They may run in one process, one library, separate processes, or separate repositories. Process placement never changes alias-observation time, deduction identity, Value order, or terminal semantics.

    Directional precedence¶

    This proposal records an owner-directed replacement of the current whole-Vessel architecture. During drafting and activation, its decided direction takes precedence over conflicting older designs. A conflict is work to supersede explicitly, not a reason to weaken or omit the new boundary.

    This precedence does not make the proposal effective semantics. Until one activation pull request changes this proposal to Accepted and synchronizes all canonical and conformance projections, authoritative main remains the conformance target. Implementations MUST freeze conflicting paths rather than silently choose between this proposal and current Accepted text.

    Motivation and reproduction¶

    SCP-0014 established a live laid Cable with channel-equivalent Goal edges, streaming multiplicity, per-input terminals, and final drainage. Its follow-up implementation plan assigned the following to one Vessel-shaped Runtime:

    • lazy deduction and mutable future structure;
    • channel buffers, backpressure, Value routing, and Host emissions;
    • input-segment state and the Outcome & Value Store;
    • Cable lifecycle and final results; and
    • a planned persistent Goal-step memo.

    That assignment hides two different state machines. Structural control may pause at an undeduced occurrence, observe a newly rebound alias, and append new topology. Channel execution must concurrently operate installed topology, preserve backpressure, and deliver Values and terminals. Treating these as one component makes the Cable handle appear to be passive state even though its data plane is a live execution engine.

    The agent-facing model exposes the stronger requirement. An Agent works by observing a result and replanning. In Subsea Cable, replanning is not an autonomous Vessel heuristic and not mutation of committed history. The Agent stores a new immutable Goal artifact and moves its alias; lazy deduction lets only later-demanded occurrences observe that revision. The Runtime architecture must preserve that feedback loop directly.

    Existing invariant under pressure¶

    The following existing invariants remain correct:

    • unqualified aliases are resolved per occurrence at demand time;
    • completed deductions and stored artifacts are immutable;
    • routed Host Values may unblock later deduction;
    • the live Runtime does not compile a prospective Cable and disappear;
    • channel order, backpressure, multiplicity, and explicit terminal frames are portable behavior; and
    • deployment topology is not language semantics.

    The ownership model cannot express those invariants cleanly because it also says that Vessel is merely a metaphor for the complete Runtime and that Carousel owns routing, frontier, lineages, and Touchdown publication. It leaves no named owner for installed channel topology or the live Cable data plane.

    Classification¶

    This is a language-level Runtime boundary, not source syntax, Scheduler policy, or a particular implementation profile.

    • It changes the canonical meanings of Vessel, Carousel, Runtime, and Cable.
    • It fixes when Agent-authored plan revisions may affect one live voyage.
    • It fixes which plane may observe aliases, carry Values, publish structure, and emit terminals.
    • It changes the portable completion condition for EndOfResult and EndOfStream by requiring structural closure as well as data-plane drainage.

    Repository layout, RPC, package names, and concrete wire encoding remain implementation choices.

    Proposed specification¶

    1. Components and authority¶

    Subsea Cable Runtime
├─ Vessel control plane
│  └─ Carousel — demand-scoped atomic deduction mechanism
├─ Cable data plane
├─ Codebase and append-only deduction ledger
├─ Scheduler port
└─ Host port

    Subsea Cable Runtime names the whole conforming deployment. No process boundary is implied.

    Vessel names the control plane. It owns the voyage, the set of existing occurrences, the undeduced frontier, coordination of structural demand, Touchdown-window accounting, deduction publication, and the determination that no further structural work remains for a segment or Cable. Scheduler remains the source of explicit demand; Vessel may initiate speculative demand only under the accepted prefetch rules. Vessel MUST NOT transport channel frames or implement buffer backpressure.

    Carousel performs one atomic deduction requested by Vessel. It resolves the occurrence's current alias when applicable, applies the selected reduction rule using supplied arguments and resolved routed values, and commits either one complete deduction record or no successful record. It MUST NOT decide the voyage course, choose an explicit or speculative demand, replenish a window on its own, own Cable lifecycle, evaluate grounded leaves, or interpret Scheduler policy.

    Cable data plane owns each live Cable's installed execution topology, input admission and queue, declaration-pin leases, lifecycle and decommission state, channel buffers, backpressure, routed Values, Host emission sessions, output-multiplicity enforcement, Outcome & Value Store, and propagation of EndOfResult and EndOfStream. It MUST NOT read a mutable Goal alias, apply a reduction rule, or create a deduction record.

    The Scheduler retains eligibility, attempts, outcome decisions, and Scheduler-addressed policy interpretation. Cable records accepted outcomes and routes their Values; that storage responsibility does not transfer outcome authority from Scheduler. The Host retains primitive semantics, function-leaf evaluation, Anchor invocation, and Host-addressed policy interpretation. The plane split does not transfer either authority to Vessel or Cable.

    2. Agent-authored replanning¶

    An Agent or operator MAY observe the authorized outward Cable surface and then publish a revised plan through Vessel's Codebase-facing control surface. Vessel owns validation, authorization, storage requests, and alias-rebind requests; Codebase owns the resulting immutable artifacts and alias state. A plan revision is committed in this order:

    1. validate the proposed source or artifact;
    2. store each new immutable artifact by content hash; and
    3. atomically move the intended Name/Arity alias to the selected full hash.

    The authoring operation does not edit an existing artifact, deduction record, installed topology item, Host effect, Value, or terminal.

    Vessel MUST NOT invent such a revision from Cable results. It may validate, store, authorize, trace, and later consume an Agent-authored revision, but the Agent or operator remains the author of the new reduction shape.

    Value-dependent conditional and lookup selection inside an already authored reduction remains distinct from replanning. The former selects among declared structure; the latter publishes a new immutable reduction artifact and alias binding.

    3. Demand-time observation and races¶

    Neither lay nor input admission pins a Codebase revision. The declarations pinned for Scheduler, Host, or forwarding policy do not pin Goal aliases.

    For an unqualified occurrence, alias selection linearizes at the atomic alias read performed by its successful deduction:

    • if the alias rebind linearizes first, the deduction selects the new hash;
    • if the deduction's alias read linearizes first, it selects the old hash; and
    • exactly one selected hash and observed Codebase revision are committed.

    This rule applies to distinct occurrences in the same active input segment. Consequently, an Agent may publish a revision after observing an early result, and a later-demanded occurrence in that segment may select it. Any occurrence already committed keeps its earlier selection permanently.

    A hash-qualified reference never consults the alias and retains its existing pinned identity semantics.

    4. State ownership¶

    State or transition Portable owner
    voyage and future structural course Vessel
    occurrence set, undeduced frontier, and Touchdown-window accounting Vessel
    lay(goalRef) and atomic creation of one voyage/Cable pair Vessel, coordinating Cable allocation
    send admission, Input(k), input queue, and decommision linearization Cable data plane
    Scheduler/Host/allowlist declaration-pin acquisition and lease lifetime Cable data plane
    plan validation, artifact-store request, and alias-rebind request Vessel Codebase-facing control surface
    one atomic alias selection and reduction commit Carousel acting for Vessel
    immutable artifact and alias index Codebase
    deduction records and structural provenance append-only ledger written through the Vessel/Carousel commit path
    installed execution topology Cable data plane
    channel capacity, buffering, and backpressure Cable data plane
    routed Values, emissions, and terminals Cable data plane
    Outcome & Value Store Cable data plane; Vessel requests only the values required for one deduction and passes them to Carousel
    evaluation eligibility, attempt lifecycle, and outcome decisions Scheduler
    accepted outcome recording and routed-value delivery Cable data plane
    policy-addressee resolution for a newly published occurrence Vessel, using the segment pin leases supplied by Cable
    Scheduler-addressed policy and scope-event projection Cable data plane to Scheduler; never to Host
    Host-addressed policy projection Cable data plane sends only hostPolicies[] on an authorized Host invocation
    grounded leaf implementation Host
    final structural and execution result assembly stateless Runtime composition layer, after the Vessel/Cable completion handshake

    No owner may infer another owner's state by reading its storage directly. A same-process implementation MUST preserve the same ports and observable order as a split-process implementation.

    lay(goalRef) is a Vessel control operation. Vessel creates the voyage and asks Cable to allocate its data-plane lifecycle; the outward CableHandle is returned only after that pair exists. lay still admits no input, pins no declaration, resolves no alias, and starts no deduction or Host work.

    send and decommision are commands on the Cable lifecycle. Cable validates a send against the target descriptor established at lay, acquires the three declaration snapshot leases through their owning registries, and owns the final admission/decommission linearization. It retains every admitted segment's leases until that segment's EndOfResult has propagated. When a segment activates, Cable gives Vessel the input tuple and immutable lease references so Vessel can create and demand the Root occurrence without repinning or pinning a Codebase revision.

    Vessel resolves each occurrence's ordered policies against those supplied leases when it publishes the occurrence. Cable projects Scheduler-addressed policies and scope events such as BeforeAttempt, Hold, and ChildScopeOutcome only to Scheduler. After Scheduler authorizes a grounded leaf attempt, Cable projects only hostPolicies[] to Host; directPolicies[] never crosses the Host boundary.

    5. Structural demand and topology publication¶

    Cable may reach an installed frontier whose continuation requires an undeducted occurrence. It reports readiness to Vessel; readiness is not demand. Vessel owns the occurrence set and therefore projects the eligible candidate fact, occurrence identity, and readiness dependencies to Scheduler. Scheduler selects a candidate and sends explicit structural demand back to Vessel. Vessel may additionally initiate speculative demand under the accepted Touchdown prefetch rules. In both cases Vessel selects or validates the exact occurrence and asks Carousel to perform exactly one deduction. Carousel does not run an autonomous replenishment loop.

    The portable boundary records are:

    StructuralDemand(occurrenceId, kind = explicit | speculative)
TopologyInstall(installId, slice)      Vessel -> Cable
TopologyInstalled(installId)           Cable  -> Vessel acknowledgement
TopologyInstallRejected(installId, reason)

    StructuralDemand records the demand Vessel acts on: explicit when it comes from Scheduler, speculative when Vessel initiates it under the prefetch rules. Cable readiness is not a StructuralDemand. A TopologyInstall carries one complete committed slice, and installId is its idempotent installation identity. Wire encoding of these records remains a Runtime profile concern.

    For each requested occurrence:

    1. Vessel supplies Carousel with the occurrence, arguments, active lineages, declaration-profile context, and only the resolved routed values required by that reduction.
    2. Carousel atomically commits the selected hash and complete reduction result.
    3. Vessel publishes the resulting structural slice to Cable as an append-only, idempotently identifiable topology installation.
    4. Cable makes the new slice eligible only after the whole installation is present. Partial installation is never observable as executable topology.

    Storage transactions across processes need not be physically atomic. Portable behavior MUST nevertheless provide an atomic publication boundary: a crash or retry may replay the same installation identifier, but it may not execute half of a reduction result, duplicate an occurrence, or select an alias again for a committed occurrence.

    Installation outcomes are reported as follows:

    • A TopologyInstall whose installId and slice content equal an installation Cable already applied is an idempotent no-op. Cable re-sends the same TopologyInstalled acknowledgement and records only a trace event; it reports no diagnostic, creates no second reservation, and publishes no Touchdown twice.
    • Cable reports TopologyInstallRejected as a Runtime contract violation, with exactly one of these reasons:
    • stale-segment — the target segment has already reached its terminal, or the Cable has completed EndOfStream;
    • malformed-slice — the slice is incomplete or inconsistent with installed topology;
    • identity-conflict — the installId was already applied with different content.

    A rejected installation installs nothing and publishes no Touchdown. It is not an ordinary segment outcome and is never converted into a Value.

    Grounded leaves in a committed slice awaiting Cable's installation acknowledgement are not published Touchdowns, but they MUST participate in Vessel's next speculation decision. Vessel atomically creates one pending-install window reservation per newly grounded leaf before it may issue another speculative demand. Speculation occupancy is:

    published unconsumed Touchdowns + pending-install window reservations

    The accepted SCP-0001 target and overshoot rules apply to that occupancy for speculation gating. Explicit Scheduler demand remains unblocked by the target. A single deduction that grounds more leaves than the remaining capacity may still produce SCP-0001's AtomicPrefetchOvershoot; an explicit demand may still produce DemandedTouchdownOverTarget. That diagnostic is decided at deduction commit/reservation creation from the occupancy above, not at installation acknowledgement. The acknowledgement only converts reservations and MUST NOT emit or re-evaluate an overshoot diagnostic. Installation latency MUST NOT create a third kind of overshoot or allow repeated speculative deductions beyond the target.

    The reservation is keyed by the idempotent topology-install identity. A retry creates no second reservation. On Cable's successful atomic acknowledgement, Vessel converts each reservation into one published unconsumed Touchdown without changing the speculation occupancy. If installation terminates in an unrecoverable failed or cancelled segment, or if decommission/drain completion terminalizes the affected segment or Cable, Vessel releases the reservation only as part of that recorded terminal path and only after terminalization makes later installation or publication impossible. It cannot use a transient failure, cancellation request, decommission request, or delayed acknowledgement to replenish speculation.

    Carousel may discover that a committed path reaches a grounded leaf before the corresponding topology installation has completed. That state is not yet a published Touchdown. A Touchdown is published, enters the SCP-0001 window, and becomes visible to Scheduler eligibility only after Cable has atomically installed the complete slice and acknowledged that installation. A failed or retried installation cannot increment the window early or twice. Scheduler's first-dispatch consumption acknowledgement is applied through the Vessel control plane's Touchdown-window accounting rather than sent directly to Carousel. The acknowledgement and prefetch target retain the observable rules of SCP-0001; only their owner and port change.

    6. Values and feedback¶

    Cable records accepted Host outcomes and emitted Values in its segment-private Outcome & Value Store. When a later deduction requires a routed value, Vessel requests that exact resolved value through the Cable read port and passes it to Carousel. Carousel never scans Cable state and Cable never applies the reduction that consumes the value.

    Authorized outward observation of right-end Values, segment outcomes, diagnostics, and terminals enables an Agent to decide whether to revise the plan. That outward observation is not an implicit alias rebind or topology mutation.

    7. Segment and Cable completion handshake¶

    Data-plane drainage alone is insufficient to prove structural completion, and control-plane structural closure alone is insufficient to prove execution completion.

    For this contract, an occurrence is reachable for an input segment when it is that segment's Root or is exposed by a committed reduction on the selected structural path, and no accepted structural or routing decision has eliminated its invocation. An occurrence in an unselected conditional or lookup branch is not reachable. A downstream invocation for which /0 or an empty /N produced no Value never becomes reachable. A reachable occurrence may still be blocked on a routed value or withheld by Scheduler; those states do not make it unreachable.

    An input segment may publish its one EndOfResult only when both are true:

    1. Vessel has no reachable undeduced occurrence, pending deduction, unpublished committed slice, or unresolved structural/value barrier belonging to that segment; and
    2. Cable has drained all installed work caused by the segment, including Host emissions and downstream channel work.

    A reachable ready occurrence withheld by Scheduler prevents structural closure and therefore prevents EndOfResult. Readiness never implies demand, but silence is not termination: the segment remains pending until Scheduler demands the occurrence or an accepted Scheduler decision terminates the relevant scope or segment. EndOfResult(Succeeded) MUST NOT be emitted while a reachable undeducted frontier remains. Structure that was never selected, or a downstream invocation that does not exist because /0 or an empty /N produced no Value, does not create such a frontier.

    The two observations form one logical completion handshake. Their concrete message order is a Runtime profile choice, but a conforming implementation must linearize one final segment-completion decision and emit exactly one terminal.

    EndOfStream requires all existing SCP-0014 conditions plus both of the following:

    • Vessel has closed structural publication for the decommissioned Cable and has no unpublished topology for any admitted segment; and
    • Cable has propagated every segment terminal and drained every installed channel and attempt.

    An Agent may continue updating the Codebase after structural closure, but those updates cannot reopen a decommissioned Cable or mutate its result.

    8. Fully Touchdown Cable¶

    The Fully Touchdown Cable remains the canonical ordered list of grounded leaf content hashes for the terminated voyage. It is not the live Cable data plane.

    Vessel supplies immutable deduction and position provenance; Cable supplies the completed segment order and execution drainage proof. A thin Runtime composition layer assembles the final result only after the completion handshake. That layer owns no structural or execution state: it only combines the two planes' immutable evidence. Outward CLI, MCP, service, and library adapters attach to this composition layer rather than to Vessel or Cable directly, and it may call each plane only through that plane's ports. Process placement and completion timing MUST NOT change membership or canonical order.

    9. Deduction result caching¶

    A persistent Goal-step memo is not required portable behavior and no SCP-0013 activation is planned by this proposal.

    Content-addressed artifacts already provide the mandatory structural reuse. Implementations may cache parsing, validation, normalization, or a pure deduction calculation as an internal optimization only if all demand-time alias observations, fresh occurrence/provenance records, Host effects, Values, Touchdowns, and terminals remain indistinguishable from an uncached execution.

    Such a cache MUST NOT skip Host evaluation or reuse an outcome. Host outcome or effect reuse requires a separately authorized Outcome Journal contract.

    10. Deployment and repository neutrality¶

    The following are conforming when they preserve the same boundary:

    • one process with separate modules;
    • an in-process Vessel library driving a Cable engine;
    • separate control-plane and data-plane services; or
    • generated deployment code linked to both responsibilities.

    Separate repositories are neither required nor forbidden. The choice follows the portable contract; it does not define it.

    As an implementation direction rather than language semantics, the owner chose to begin the external implementation in the single vessel repository. The control, Cable, and boundary modules are separated there and enforced by import-boundary tests. Splitting repositories is reconsidered after the ports stabilize.

    Alternatives¶

    Alternative Benefits Costs/reason rejected
    Keep Vessel as the complete Runtime metaphor Minimal documentation change Hides the live Cable engine and gives no enforceable control/data ownership boundary
    Make Carousel the control plane Reuses an existing component name Carousel is intentionally a demand-scoped deduction mechanism, not the voyage or replanning authority
    Let Cable resolve aliases and deduce Fewer cross-plane calls Lets execution state choose Goal topology and destroys the unique deduction owner
    Let Vessel autonomously rewrite plans from outcomes Closed automatic loop Replaces Agent intent with an unspecified planner and makes audit authorship false
    Fully compile, then run a detached Cable Simple execution engine Cannot observe later alias revisions or value-dependent structural barriers in one live voyage
    Require separate processes or repositories Strong physical isolation Makes deployment topology language semantics and raises adoption cost without strengthening the logical contract
    Keep persistent Goal-step memo as a core feature Possible repeated-work savings Adds keys and cross-revision hazards before profiling shows value; does not reuse occurrences or Host effects

    Philosophy and boundary audit¶

    • Structure remains distinct from execution policy: Agent revisions and Carousel deductions change future structure; Scheduler policies do not.
    • Goals remain declarations of dependency and routing; Host functions remain concrete leaf implementations.
    • Policy erasure continues to preserve topology except where an already accepted policy contract explicitly controls demand or completion.
    • Vessel, Carousel, Cable, Scheduler, and Host each have one non-overlapping authority.
    • Unqualified aliases remain demand-resolved per occurrence, including after an Agent-authored rebind in the same live segment.
    • Completed deductions and installed topology remain immutable.
    • Value routing remains explicit. Vessel requests one required resolved value through the narrow Cable-owned port and passes it to Carousel for that deduction; Carousel never calls the Cable port directly.
    • The boundary is portable across languages, processes, and infrastructures.

    Compatibility and migration¶

    • Previously valid source affected: none.
    • Previously invalid source newly accepted: none.
    • Stored artifact/hash impact: none; Goal, Structure, and artifact hashes do not include process placement or plane identity.
    • Diagnostic impact: no source diagnostic changes. New Runtime protocol diagnostic TopologyInstallRejected(reason = stale-segment | malformed-slice | identity-conflict); a duplicate identical installation reports no diagnostic.
    • Migration strategy: first activate the terminology, ownership table, completion handshake, and conformance cases; then update external ADRs and split implementation work along the activated boundary.
    • Version/profile requirement: a Runtime advertising this boundary must pin the activation revision. Older whole-Vessel profiles remain identifiable as older contracts and must not claim the activated profile.

    Existing implementations are evidence, not authority. Code may be retained only after its responsibility is classified under the new table.

    Grammar and conformance impact¶

    • README.md: rename the whole deployment to Subsea Cable Runtime; describe Vessel control, Cable data execution, Agent revisions, and completion handshake.
    • METAPHORS.md: make Vessel the navigator/control plane and the laid Cable the live carrier/data plane; keep Carousel as the deduction mechanism.
    • FOR_AGENTS.md: make the Agent-authored replan loop explicit and distinguish it from declared conditional selection.
    • AGENTS.md: replace the whole-Runtime Vessel rule and add the plane boundary.
    • Runtime guides: reassign Outcome & Value Store, channel operation, Touchdown publication, and lifecycle responsibilities.
    • ANTLR/EBNF: no changes.
    • source diagnostics: no changes.
    • conformance additions:
    • an Agent observes an early result, stores H2, and rebinds an alias before a later occurrence is demanded; that occurrence selects H2;
    • an occurrence committed to H1 remains H1 after the rebind;
    • two occurrences in one active segment may record different Codebase revisions according to their demand order;
    • a concurrent alias rebind and deduction select exactly one revision;
    • Cable cannot resolve an alias or create a deduction record;
    • Vessel cannot synthesize a Value or terminal without Cable evidence;
    • topology installation is atomically observable and idempotent on retry;
    • same-process and split-process profiles normalize to identical deduction, topology, Value, and terminal traces using the identity and transport-event normalization in conformance/DEDUCTION.md Section 18, extended only with the idempotent topology-install identity and plane-local transport events;
    • EndOfResult and EndOfStream require both structural closure and data-plane drainage; and
    • an Agent update rejected by artifact validation or stale expectedRevision leaves the current alias target, committed deductions, and installed topology unchanged, so later demand observes the existing alias;
    • Scheduler withholding a reachable ready occurrence leaves the segment pending and emits no EndOfResult; demand or an accepted Scheduler terminal decision is required before completion;
    • before Cable acknowledges installation, a grounded leaf is invisible to Scheduler eligibility and the published Touchdown window but occupies exactly one pending-install reservation for speculation gating; retrying the same installation creates no duplicate reservation or publication, and delaying the acknowledgement admits no additional speculative demand;
    • BeforeAttempt, Hold, ChildScopeOutcome, and other Scheduler-addressed scope events reach Scheduler only, while Host receives hostPolicies[] and never directPolicies[];
    • segment activation uses the declaration leases supplied by Cable to create the Root occurrence and performs no repin; and
    • lay returns a CableHandle only after both the Vessel voyage and Cable data-plane lifecycle exist, while still creating no segment, pin, occurrence, deduction, or Host work;
    • re-sending an identical TopologyInstall yields the same TopologyInstalled acknowledgement with no diagnostic. An installation for a terminated segment yields TopologyInstallRejected(stale-segment), and a reused installId with different content yields TopologyInstallRejected(identity-conflict); an incomplete or internally inconsistent slice yields TopologyInstallRejected(malformed-slice). No rejected case installs any topology or publishes a Touchdown; and
    • the final Cable result is identical whether the composition layer runs with the planes in one process or across a process boundary, and no outward adapter bypasses the composition layer to read plane storage.

    Reference experiment¶

    No implementation is normative for this proposal. After the boundary is reviewed, external ADRs and a bounded experiment must demonstrate:

    • separate in-memory control/data modules connected only by the proposed ports;
    • a mid-segment Agent-authored alias rebind observed by a later occurrence;
    • idempotent replay of one topology installation; and
    • identical normalized traces when the same ports are moved across a process boundary.

    The experiment must not begin by preserving the current whole-Vessel package shape and then describing it as evidence for this proposal.

    Unresolved questions¶

    None. The four questions raised during Discussion were decided by the owner on 2026-09-28 (PR #23 comment) and are incorporated above:

    1. boundary record names: StructuralDemand, TopologyInstall, TopologyInstalled, and TopologyInstallRejected (Section 5);
    2. final result assembly: a stateless Runtime composition layer (Sections 4 and 8);
    3. installation diagnostics: an identical duplicate is an idempotent no-op; stale, malformed, and identity-conflicting installations are TopologyInstallRejected contract violations (Section 5); and
    4. repository start: a single vessel repository with enforced module boundaries, recorded as implementation direction only (Section 10).
