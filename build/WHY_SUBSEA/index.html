    Why Subsea Cable: "How Did I Get Here?"¶

    Subsea Cable attaches intent to every step it takes.

    Status of this page

    This page explains why Subsea Cable exists and how it differs from other tools. It is an explanatory projection, not a semantic authority. On any difference, follow the sources listed in GOVERNANCE.md, especially the Language Reference. Where a pattern below depends on something not yet decided, the page says so and links the open item.

    Can you answer this right now?¶

    A long task hits an exception nobody anticipated. Or the context was compacted, or the session dropped and resumed.

    • Which decisions led to the step you are on now?
    • Which of those decisions was wrong?
    • How far back do you need to go, and which effects on the world have already happened since then?

    Today an agent answers these questions by rereading its transcript and guessing. It goes back too little and patches a symptom, or, unsure, goes back too far and redoes work that was fine. Adding Airflow or Temporal does not change this. Those engines answer "how do I resume the steps I was given?", not "what was I trying to do when I got here?"

    In Subsea Cable, the first question is meant to be a lookup, not an inference. Every committed deduction of a named Goal records the full ArtifactHash it selected and the lineages it extended; an inline Goal-arrow stage takes its identity from the enclosing artifact. The intent behind each grounded leaf is therefore recorded rather than reconstructed. The judgment that remains, deciding which decision was wrong, operates on a small, bounded set of candidates instead of an entire transcript. How much of that record an Agent can query while a voyage is still running is a Runtime capability, described in section 2.

    The problem: unstructured work is fixed while doing it¶

    Agent work shows what every business already knows: open-ended problems cannot be predicted or modeled cleanly in advance. Three things still hold.

    1. Higher Goals change less. Plans near the leaves are often wrong, but the Goal being pursued and its nearby ancestors are comparatively stable. Most corrections are therefore local, and the natural scope of a correction is the lowest common ancestor that contains both the bad decision and its consequence.
    2. You must be able to try, look, and revise the Goal. Choosing a wrong or unfavorable Goal is not a failure of the method. It is the normal condition of open-ended work.
    3. Revising requires the history so far. Knowing the parent Goal is not enough. To see which decision led to which result, and to redesign exactly that point, you need every leaf reached so far, in order, together with the lineage of each one.

    The rarest and most expensive case is when a high-level Goal itself was wrong. History is useful here as well: the evidence for "this Goal was wrong" remains on the Cable with its lineage, so even the decision to change the objective has recorded grounds.

    Subsea Cable records this entire structure. Goal definitions are kept as hash-identified artifacts, grounded work is kept as the Cable, and the two are joined through deduction records and lineage. That is why it fits work that has to be corrected while it is being done.

    Why now: evaluation erases abstraction¶

    Evaluation keeps what was computed. Subsea Cable keeps what was intended.

    "Just call the function" used to be right¶

    The essence of evaluation is erasing abstraction.

    • β-reduction replaces a redex and, at that moment, forgets what the call was for.
    • Graph reduction in Haskell overwrites a thunk with its value and discards the "why".
    • The call stack is the closest thing to a Goal boundary, but a frame is popped the moment it returns.
    • Even when a program is data, as in Lisp, keeping the history is an overhead bolted onto evaluation.

    That was reasonable. The executor (the CPU) never needed the "why", and the one who did (the programmer) could reread the code offline. Keeping abstract structure at run time was a cost nobody consumed. Until LLMs started solving open-ended problems the way people do, a deduction whose structure stays visible was a luxury slower than a function call.

    What changed¶

    The executor now consumes the "why" itself. To decide what to do next, an LLM needs to know, at run time, "what was I trying to do when I got here?" Abstract structure has turned from a disposable by-product into a run-time input.

    The cost argument flipped as well. When a single leaf is an LLM call or an external effect that takes seconds, the cost of maintaining Goal boundaries through deduction is within the noise.

    Same roots as Haskell, a different purpose¶

    Subsea Cable inherits Haskell's philosophy and was inspired by β-reduction. Its purpose is different.

    Haskell Subsea Cable
    Purpose of reduction Obtain a value Keep Goal boundaries available
    The reduction process Can be forgotten Is itself the record: each deduction is a commit
    Replacement Redex is replaced by its result Children are exposed and each lineage is extended
    Analogy A computation that vanishes when done A call stack that is never popped, whose frames are joined to hash-identified definitions

    Subsea Cable's concern is not evaluation. It is being able to keep answering "so what were we trying to do?"

    The nearest prior work¶

    Self-adjusting computation (Adapton and related systems) keeps the dependency trace of a run and recomputes only what changed when inputs change. Structurally this resembles Cable reuse. The purpose differs.

    • Self-adjusting computation keeps the trace for computational efficiency, and the trace has no intent boundaries.
    • Subsea Cable keeps intent boundaries so that an author, human or agent, can redesign. Reuse is a side benefit.

    1. Two records¶

    1.1 Goal definitions: intent fixed by hash¶

    • Every authored Goal definition is stored as an immutable artifact identified by its ArtifactHash.
    • A name is only an alias, a Name/Arity pointer into the Codebase. Changing a definition stores a new artifact and moves the alias.
    • The fact that "at that point, this Goal had this structure" is never lost.

    1.2 Deductions and lineage: context on every step¶

    • When a named Goal occurrence is demanded, its reference is resolved and the selected full ArtifactHash, arguments, resulting structure, active lineages, and (for an unqualified reference) the observed Codebase revision are committed together in one deduction record.
    • An inline Goal-arrow stage such as [{code, logs}] -> Diagnose[code, logs] is deduced too, but its record has referenceKind = inline-arrow, no requested name, and no artifact hash: the enclosing artifact supplies its identity, and it adds no lineage segment (Runtime Contract §8.1).
    • A deduction extends each incoming lineage across the edges it commits. Lineage segments are Name/Arity, for example CreateOrder/1.RegisterOrder/1.ValidateStock/1; the hash each segment's occurrence selected lives in that occurrence's deduction record, not in the segment itself.
    • So even a leaf that has already reached Touchdown has a recorded chain of deductions that produced it.
    • When a laid Cable has been decommissioned and drained, a Runtime that claims the voyage-result capability exposes the Fully Touchdown Cable, the ordered list of published grounded leaf hashes, with a provenance index that maps each position back to its deduction ancestry (Runtime Contract §12).

    1.3 Joined: one record answers several questions¶

    Question Where the answer comes from
    Which grounded work is this? Its Touchdown content hash
    Under which intent was it grounded? Its lineage, joined to the ArtifactHash each named-Goal deduction on that lineage selected
    Is that intent still current? Compare each recorded ArtifactHash with what its alias resolves to now

    Current lineage limitation

    Lineage segments identify Goals by Name/Arity. Current analysis must use the recorded artifact hashes alongside those names when aliases change during a voyage. Hash-addressed lineage segments are not available in the current language contract.

    2. What this makes possible: replanning after an unexpected failure¶

    The hardest moment for an agent is "this didn't work, and I never considered why." Subsea Cable is designed so that this moment can become a procedure. The steps below are an authoring pattern, not a Runtime algorithm defined by the language, and Vessel never invents a plan change by itself; the agent authors it.

    What is portable today, and what needs more

    The portable outward Cable surface exposes right-end Values, segment outcomes, diagnostics, and terminals (SCP-0015). It does not expose a failing leaf's own outcome or its deduction ancestry while the Cable is live. Deduction ancestry is composed into the voyage result only after decommission and drainage, and the normalized trace in Runtime Contract §11 is an evidence and profile contract, not a portable live Agent query.

    So the walk-back below works after the fact against a drained voyage result from a Runtime that claims voyage-result, followed by a revised new voyage. Doing it mid-voyage requires a Runtime-profile extension or a future contract for live provenance queries; see Open problems.

    1. Observe. Read the segment outcome, diagnostics, and terminal from the outward Cable surface.
    2. Find the cut by walking back. Using the provenance index, walk the reached leaves backward from the failure and inspect each one's deduction ancestry and recorded artifacts. The regression point is the first leaf produced by the deduction that carried the wrong assumption. Choosing that deduction is still a judgment, but you only need to look a short way back, not re-review the whole tree.
    3. Scope with the lowest common ancestor. The common ancestor of the cut and the failure is the smallest scope that contains both the bad decision and its consequence. Its Goal structure ("what we meant to do") and the records after the cut ("what actually happened") are the complete context for replanning.
    4. Revise without rewriting history. Store the revised definition as a new immutable artifact and rebind its alias. Undeduced occurrences observe the new definition when they are demanded; committed deductions never change. If the part to revise is already committed, start a new voyage and reuse unchanged structure from the earlier one (SCP-0004). Structural reuse never by itself permits skipping Host effects.
    5. Keep the abandoned attempt. Nothing is deleted: committed deductions and published Touchdowns stay as history. A $ leaf in that history marks a potential effect boundary, not evidence that an effect happened. Cable membership includes leaves that were withheld, discarded, never dispatched, failed, or cancelled, and Host effects are opaque and never rolled back. Whether an attempt ran, and what it did, comes only from attempt and outcome evidence, or from a separately authorized Outcome Journal.
    6. Bound the loop. Preventing endless regression to the same point is a Scheduler concern expressed through @policy, not a structural one. Concrete policy semantics for this are not defined yet; see Open problems.

    3. Compared with the agent loop¶

    An LLM agent loop today is essentially:

    while (!done) {
  action = model(transcript)
  result = tool(action)
  transcript.append(action, result)
}
    Aspect Current agent loop Subsea Cable
    Where the plan lives Natural language in the transcript Hash-identified Goal artifacts
    Execution history Text in the transcript Deduction ledger and the ordered list of reached leaves
    Link between history and intent None; reread and reinterpret every time Lineage joined to hash-identified artifacts through deduction records
    Regression point after failure Guessed by reading backward Bounded by walking back through deduction ancestry (after drainage today)
    Replanning context The whole transcript, too much or missing pieces Lowest-common-ancestor structure plus the records after the cut
    Effects that may have been applied Depends on memory $ leaves mark where effects could occur; attempt and outcome evidence, or an authorized Outcome Journal, say which ran
    Resuming after context loss "Where was I?" is guessed Committed deduction records plus the undeduced frontier
    Context for a sub-agent Summarized by hand A leaf's arguments and its lineage

    A transcript does contain both the "why" and the "what". It mixes them as unstructured prose, so they cannot be split or joined mechanically. That is why regression decisions become guesswork.

    4. Compared with workflow technologies¶

    4.1 How each family records intent and history¶

    Family Examples "Why" (intent structure) "What" (execution history) How they are linked
    Declarative static DAG Airflow, Step Functions, Argo, Dagster A DAG or state-machine definition, pinned per run where the product supports it Task-instance records Per run; no per-occurrence deduction context
    Code-based durable execution Temporal, Restate Hidden in imperative code, with no address Event history Reconstructed by replay; changing code risks non-determinism
    Hash-based builds Nix, Bazel Derivation or action graph, by hash Output hashes Linked, but static; no in-run strategy change and no effect model
    Subsea Cable — Every Goal artifact by hash, plus the realized paths Deduction ledger and published leaves Named-Goal deductions record the selected artifact and lineages; inline stages inherit the enclosing identity; the undeduced frontier stays revisable

    4.2 Granularity of "change the plan while it runs"¶

    Unit of change Cost
    Airflow 3 Depends on the DAG bundle: a versioned bundle (for example Git) keeps a run on the bundle version it started with; Local, S3, or GCS bundles can pick up the latest code, and clearing a task may rerun it on the latest bundle version depending on configuration No per-occurrence record of which definition produced which task
    Step Functions An execution already running keeps the definition it started with Changing the plan means starting a new execution
    Temporal Versioned branches in workflow code (patching, worker versioning) Developers manage determinism; mistakes surface as non-determinism errors
    Nix / Bazel The build There is no notion of "during the run"
    Subsea Cable The occurrence: the past is committed, only the undeduced frontier observes new definitions No replay of authored code; committed records are reused as they are

    4.3 The same failure, four ways¶

    "An unexpected exception mid-run. One of the earlier decisions was wrong."

    • Airflow: retry the failed task or rerun the whole DAG. Nothing points at the wrong decision.
    • Temporal: someone must have written the handling code in advance, and the point to return to lives in that author's head.
    • Nix / Bazel: fix the input and rebuild. The cache helps reuse, but changing strategy mid-run is out of scope.
    • Subsea Cable: walk back through deduction ancestry to the cut, scope with the lowest common ancestor, publish a revised artifact, and let the frontier or a new voyage observe it while reusing structure that remains valid. Every step starts from records (after drainage today; live queries are an open item).

    5. Why this is hard to substitute¶

    1. Existing tools keep only one of the two records completely, or keep both statically.
      • Static DAGs: the definition exists independently of any run, but its link to execution history is run-level (pinned per run where the product supports it), not per occurrence.
      • Durable execution: the "why" is hidden in code and has no address.
      • Hash builds: both exist, but nothing changes during a run.
      • Agent loops: both are mixed into prose.
    2. Subsea Cable joins the two records through deduction records and still keeps the frontier open. "The past is immutable evidence; the future can be revised from that evidence" holds within one model.
    3. This targets exactly the agent's bottleneck. What agents lack is not durable execution, which existing engines already provide. It is knowing where to start rethinking after a failure, and why. Subsea Cable turns locating that point from inference into lookup.

    6. What adopting these guarantees involves¶

    Writing a Goal graph is the beginning. Using it as evidence for replanning means that the record must remain trustworthy when work fails, outputs arrive at different times, and an alias changes while a voyage is live.

    What you want from the workflow What the Runtime must keep consistent
    Revise work that has not committed yet Demand-time alias selection and immutable committed history
    Explain why a leaf was reached Selected artifacts, occurrences, lineages, and the provenance that joins them
    Handle parallel or streamed results Value routing, backpressure, multiplicity, and explicit completion
    Revisit a failed attempt Structural evidence distinguished from actual Host execution and effects

    These responsibilities interact. A parser or a successful happy-path demo does not establish them. Choose an implementation by its pinned specification, supported capabilities, reproducible conformance results, and recovery limits. You can spend your integration work on the Voyage Plan and genuine Host leaves while its maintainers verify the execution contract.

    The adoption guide describes that boundary. Runtime availability separates dated implementation evidence from the scenarios still in progress. It does not promise an available production release or a delivery date.

    7. Open problems¶

    These capabilities are not part of the current portable contract:

    • Live provenance queries. The outward surface does not provide a portable query for a failing leaf's outcome and ancestry while a Cable is live.
    • Lineage-conditioned policies. The language does not define a portable policy that chooses behavior from provenance history.
    • Automatic compensation. Reusing structural evidence does not establish whether a Host effect happened or authorize an undo.
    • Automatic replanning. An Agent or operator authors plan changes; the Runtime does not invent them autonomously.

    The specification may describe a workflow pattern before a released Runtime supports it. Check Runtime availability before depending on execution or recovery, and use the adoption guide to prepare a workflow and its explicit Host boundaries.
